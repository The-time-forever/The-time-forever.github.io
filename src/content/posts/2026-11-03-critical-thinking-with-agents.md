过去，人们教导我们，批判性思维就是怀着谦逊的好奇心和适度的怀疑去接触新信息——兼听则明，形成自己的独立判断。这话至今没错，但问题在于：**如今我绝大部分的工作都交由 Agent（智能体）流转，日常工作中已经越来越没有什么能“逼”着我去进行批判性思考了。**

致所有已经深度拥抱 Agentic 工作流（同时并行跑着好几个会话，并且坚信模型还会越来越强）的工程师和产品经理们，我想先表个态：我是这些工具的死忠粉，写这篇文章绝不是劝大家少用 Agent。我的目的，是帮大家在这个“万物皆可甩给 Agent”的时代，依然能守住批判性思维。

过去，我们绝大部分的认知加工与审美判断，都发生在“提出问题”到“得出答案”之间的那段留白里。而现在，这段留白被压缩到了以秒计算。你越是高频使用 Agentic 工作流，保持思考就越难（尽管难的点可能和大家预想的不太一样）：随着模型能力越来越强，低级、明显的错误率正在大幅下降。许多（甚至绝大多数？）输出不仅文笔流畅，而且基本正确，根本不会让你产生“再多看一眼”的念头。

就算你同时开着十几个 Agent 并发干活，盯着产出结果的，终究只有你那一双眼睛。

> 💡
>
> **核心观点**：你必须刻意把批判性思维“嵌入”日常工作流中，因为系统默认并不会帮你做这件事。

之所以很难自我纠偏，部分原因在于 Agentic 工作流用起来实在是太爽了。在忙碌的一天里，能秒级获得流畅、赏心悦目且大概率正确的答案，简直是一种享受；但正因如此，人也最容易彻底放松警惕。

## 减负、让渡与缴械

每次和人聊起这个话题，我都会把它描绘成一条从高到低的阶梯：

1. **最高层：认知减负（Cognitive offloading）** —— 把具体任务委托给 AI，但自己牢牢握着结果的主导权（Ownership）。我整天都在这么干，你们也该如此。
2. **中间层：认知让渡（Deferral）** —— 工具的输出直接成了你下一步的输入，AI 给出的结果不再是一个“待验证的假设”，而是被默认当成了事实。
3. **最底层：[认知缴械](https://addyosmani.com/blog/cognitive-surrender/)（Cognitive surrender）** —— AI 的产出悄无声息地变成了你自己的观点，你甚至觉得完全没必要去检查一遍。

“认知缴械”是沃顿商学院的 [Steven Shaw 和 Gideon Nave](https://ssrn.com/abstract_id=6097646) 提出的概念。它精准地刻画了我所观察到的现象：随着对工具的信任（或者说人的惰性）不断增加，人们会顺着这条阶梯一路向下滑落。这种滑坡极难察觉，因为每一步都是渐进的，而且听起来都合情合理。上一次的回答你认真通读了，所以下一次你就只扫一眼；再下一次，你只看个大纲骨架；直到有一天，别人问起某一行代码是干嘛的，你哪怕开着 Agent 帮忙，也解释不出个所以然来。

这就是“认知缴械”，也是**“认知债务”（Cognitive debt）**不断累积的过程。这种债务通常只有在你试图调用脑海中的“系统心智模型”，却发现大脑一片空白时才会暴露。[Margaret-Anne Storey](https://margaretstorey.com/blog/2026/02/09/cognitive-debt/) 曾撰文探讨过这种现象在团队中的表现：大家对系统底层共同逻辑的理解正在不断瓦解。我也曾写过代码领域的对应概念——**[理解债务](https://addyosmani.com/blog/comprehension-debt/)（Comprehension debt，由 Jeremy Twei 提出）**。

在当下，这种债务是完全隐形的：代码库看起来干净整洁，测试用例全绿通过。直到某天你必须对系统动刀修改时，才惊觉整个团队里已经没人真正懂它了。同样地，当你只扫了一眼战略文档或产品规格书（Spec）的目录就大笔一挥签字通过时，情况也是一模一样。

把话说清楚，我并不是在提倡去做不可能的事。现代大型代码库如此庞大，指望在脑子里装下完整的心智模型是不现实的。[Claude Code 团队就曾公开表示](https://claude.dev/blog/solving-code-review-at-anthropic/)，他们采取的是“按需重建理解”：需要理解哪一块，就让 Claude 专门解释那一个切片，而不是硬塞进大脑。正如我[之前写过的](https://addyosmani.com/blog/intent-debt/)，这类债务其实比大多数工程师想象的更容易偿还。你不需要时刻维持全局模型，只要能在需要时局部重建出来就行。关键在于，**你得清楚自己不知道什么**。

> 🎯
>
> **边界原则**：在试错成本低的地方，尽管放手全权委托；但在那些需要你负责的正事上，判断自己是否已经滑向底层的“认知缴械”，有一个简单的标准——**当别人问起某个问题，你连借助 Agent 现场解释都解释不清时，你就已经彻底交出了主导权。**

当然，全权委托也并非总是坏事。就在前阵子，我为了录一门课程，得从三家评分差不多的酒店里挑一家作为拍摄场地。我没时间一条条去翻住客评价，就直接把决定权交给了 AI。结果很理想，下次我还会这么干。但是，在决定怎么投资理财、怎么给孩子做职业规划，或者在工作中决定“我们要做什么产品、哪些改动会影响哪些用户、现在上线是否安全”时，我绝不会这么做。

**犯错代价低廉的活，尽管甩手；后果需要他人买单的决策，必须亲自思考。**

## 我常用来拷问自己的几个问题

过去，每当我拿不准主意时，通常会翻出一张基础问题清单来问自己：我怎么知道自己正在解决“正确的问题”？我怎么知道自己用的是“正确的方法”？有证据支撑我的结论吗？我怎么知道这事算“干完了”？大多数时候，这其实就是最经典的 [5W1H 分析法](https://addyo.substack.com/p/critical-thinking-during-the-age)（何人、何事、何地、为何、何时、如何）。白纸黑字写出来，看着甚至有点幼稚，但它能强迫你从那些平时容易忽略的维度去思考。而如今，人太容易直接跳过这一切，张嘴就问 Agent：“你觉得我该怎么办？”下面是我现在用来拷问自己的“升级版”问题清单：

- **在提问之前，我先形成自己的假设了吗？**
在让 Agent 处理任何稍微复杂点的任务前，我都会先写下（哪怕只是在脑子里过一遍）我认为的答案可能是什么。猜错了也没关系，有了新信息随时可以推翻重来。但一旦你先入为主地读了一篇 AI 写的、文笔极佳的回复，你就很难再跳出来想象其他可能性了。如果你对某个领域真的一无所知，那就让模型做一次 Thariq Shihipar 所说的**[盲区排查](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)（Blind spot pass）**：把你已知的信息喂给它，让它帮你找出那些“你不知道自己不知道”的盲点（Unknown unknowns）。
- **我是让它“帮我思考”，还是让它“替我思考”？**
这两种用法都没问题，前提是你自己得门儿清，此刻你到底在用哪一种。
- **在什么前提下，这个结论会是错的？**
找出来，然后去验证。模型自己评估的“置信度”远不如你亲自跑一个测试来得实在，所以给它设个局测一测。
- **我听过来自不同角度的反面论证吗？**
当我对某个相对开放的问题抱有强烈立场时，我会让不止一个模型去扮演“反方辩手”来驳斥我，然后审视它们的输出，再形成我自己的最终判断。这确实更花时间，但最后我对这个议题的理解会深得多。
- **如果把这东西摆在日后负责维护它的人面前，我敢拍着胸脯为它担保吗？**
这条准则适用于代码，也适用于你交付的任何其他产出。在我看来，这就是“可问责性”（Answerability）的底线。
- **有哪些技能，我已经不再亲自上手练了？**
也许是一些日常的 Bug 排查。放手丢掉一部分基础活我是能接受的，但我希望这是我“有意为之”的选择，而不是不知不觉的退化。

## 把“验证”变成一种肌肉记忆

最近我写了很多关于“验证”（Verification）的文章，因为我深信，[**软件开发的瓶颈已经从“写代码”转移到了“确信自己写对了”**](https://addyo.substack.com/p/agentic-verification)。当你给 Agent 配齐了自我验证的手段——无论是端到端测试（E2E）、属性测试（Property tests），还是真实的应用交互——它就能在你还没来得及看一眼之前，自己完成 `修改代码 -> 跑通验证 -> 读取输出 -> 再次尝试` 的完整闭环。这就是 Boris Cherny 所说的**[“给 Claude 一种验证自己工作的方式”](https://x.com/bcherny/status/2007179861115511237)**，我认为这是用好 Agent 拿高分的最核心要素。你的工作重心不再是逐行阅读代码，而是搭建这些验证闭环，并审阅最终的证据。

但“验证”本身也是可以“缴械”的。“有证据支撑我的结论吗？”很容易退化成“检查项变绿了吗？”。Agent 让生成测试变得极其廉价，于是你的屏幕上会亮起一片绿灯，但你完全可能拥有一套“全绿通过”的测试，却漏掉了一个已经跑崩的功能。如果测试用例在编写时就犯了和业务代码一模一样的逻辑错误，它照样能亮绿灯。而且，一个绿勾往往只证明了某一个维度的属性，人们却很容易产生“万事大吉”的幻觉。

> ✅
>
> **验证铁律**：当测试亮起绿灯时，先问问它证明了什么，再问问它没证明什么。

必须在动工前就把“什么叫验证通过”的标准定义清楚——因为到了事后，人们总能为任何结果找到合理化的借口。

Agent 干活的终点线必须是实打实、可触摸的证据：跑通的测试、界面截图、运行日志或链路追踪（Trace）。这能确保“完工标准”是基于客观事实的，而不是靠“看起来好像搞定了”这种模糊感觉去自由发挥（并最终缴械）。当你收到 Agent 发来的“任务完成”通知时，**在去看它的总结报告之前，先去检查它实际执行的那段命令代码以及原始输出。**

Claude Code 还可以（通过新开一个干净上下文的 Subagent）对自己的工作进行自我批判，作为一道理智检查（Sanity check）。你非常值得把这个动作固化进工作流里，让它每次自动运行，而不是等你想起来才做。我自己直到现在，每次干完活还是会习惯性补问一句：“我漏掉什么了吗？”听起来有点傻，但事实是，每当我用前沿大模型搞定一个复杂功能、自己也检查过一遍之后，只要再补问这句“我漏掉什么了吗？”，它往往还能给我拎出两三个盲点来。这就是我百问不厌的原因。

当然，没必要事事都这么大动干戈，懂得“什么时候该深挖”本身就是一种本事。我们[关于 Claude Code 团队如何做代码审查的文章](https://claude.dev/blog/solving-code-review-at-anthropic/)里，有一条我最喜欢的经验法则：**“如果你说不清楚现有的自动化检查会漏掉什么，那就老老实实请求人工深度 Review，别图快而直接点通过。”**

这条原则在写代码之外同样适用。如果 Agent 帮你汇总了五十份客户访谈记录，或者写了一份竞品分析，去抽查几份原始文档，确保摘要没有胡编乱造；去核对一下支撑你核心建议的那个关键数据，确保算式没出错。

**Agent 让“搭建验证机制”的成本变得很便宜，但真正考验你的，是知道“什么才叫好的验证”。**

## 真正把注意力放在生成的内容上

假设 Agent 给你甩过来一个 600 行的 PR（代码合并请求）。你大概扫了一眼代码结构，没逐行细看。变量命名看着挺合理，测试也全过了，于是你点了批准。但就在这 600 行的某个角落里，某处数据库事务边界（Transaction boundary）的操作先后顺序被微妙地调换了，或者某个你压根没想到的边缘情况（Edge case）的默认值被悄悄改反了。要说你没 Review 吧，你确实看了；但你盯着的，只是那些你原本就想得到要去检查的地方。

写代码和审查代码是两种截然不同的技能，[当审查流于表面时，Review 就变成了毫无意义的“盖章”（Rubber stamping）](https://addyo.substack.com/p/the-80-problem-in-agentic-coding)。所以，看代码差异（Diff）时，要假设这不是 AI 写的，而是个真人同事写的；更进一步，要穿透代码表面，去审视 Agent 在背后替你做了哪些决定。在一个漫长的会话中，它其实悄悄替你拍板了无数个小细节：默认值设多少、哪些功能被划出了范围，以及当两个需求互相冲突时，它自己脑补曲解了哪一条。

在 Agent 那份写着“一切顺利”的总结里，你绝对看不到这些隐秘的决断。所以，**直接让它把做过的所有决定和假设列成一张清单**。然后，考考你自己。随机挑几行代码问自己：这行是干嘛的？那行又是干嘛的？如果是审阅文档，合上屏幕，试着凭记忆默写出它的核心论点。有些人处理长会话有个我非常喜欢的习惯：让 Claude 写一份改动报告，并在报告末尾给自己出一套随堂测验，立下的规矩是：[**“只有测验拿满分，我才合并代码。”**](https://claude.com/blog/a-field-guide-to-claude-fable-finding-your-unknowns)

> 🛡️
>
> **交付底线**：对你亲手交付的东西，要做到心中有数、能把来龙去脉讲得清清楚楚。因为指不定哪天，就会有人跑来刨根问底。

反过来，Agent 也可以用来守护你的注意力。比如，我维护着一个开源项目，每天都会收到海量 PR。我会让 Agent 帮我初筛：哪些是新进来的、哪些违反了我们的贡献指南、哪些地方最可能需要我亲自介入。我极少让 Agent 自己拍板做最终决定，但它们能帮我把海量信息缩小到“我真正该把注意力投向哪里”，这样我就能腾出精力去思考核心问题：这些改动到底是不是在用正确的方式解决正确的问题。

接下来是“吞吐量”的问题，在这点上你必须对自己诚实。我把这叫做**[编排税（The orchestration tax）](https://addyosmani.com/blog/orchestration-tax/)**——也就是“Agent 批量产出的东西”与“你真正敢放心签上自己大名的东西”之间的巨大鸿沟。如果待审核的成品堆积的速度已经超过了你消化的速度，再开一个新的 Agent 会话不仅帮不了你，反而会害了你。在解决这个瓶颈之前，你只有两条路：要么把自动化检查的标准收得更严，减少需要你人工介入的数量；要么，主动慢下来。

**当你产出的东西多到连你自己都兜不住底时，你已经不是在做 Review 了，你只是在祈祷别出事。**

## 垃圾进，垃圾出（Quality in, quality out）

人类的心智模型依然在起作用，只不过它不再卡在执行过程的“中间”，而是转移到了“最前端”和“最末端”。你要把精力倾注在前端的“任务描述与上下文构建”，以及后端的“产出审查”上。正因如此，高质量的输入才对输出质量起着决定性作用——在我看来，**写好提示词（Prompting）本身就是一种批判性思维技能。**

在过去，如果你提了一个含糊不清的需求，接活的同事肯定会反问你、挑战你，于是你猛然惊醒：“哦等等，这事其实我自己都还没想明白。”但 Agent 往往不会这么拦住你。它会脑补填满你留下的所有空白，然后交给你一份“看起来已经完工”的答卷，哪怕支撑这份答卷的底层想法依然一团浆糊。我曾把这种现象称为**[意图债务（Intent debt）](https://oreillyradar.substack.com/p/the-intent-debt)**——那些原本应该存在、却被你偷懒省略掉的隐性目标、约束条件和底层逻辑。与其他债务不同，这笔债谁也替你还不来。**“意图”只能源自你自己。**

> 🪞
>
> **提示词即镜子**：你的提示词就是你对问题理解程度的镜子；如果你连写都写不清楚，那说明你自己脑子里也还没理顺。

在向 AI 求助之前，先用你自己的话写一份简明的需求说明书（Brief）。把目标受众、不在范围内的事项（Out-of-scope）以及“完工标准”写清楚。如果改了两轮提示词，AI 的输出还是不对味，别再打补丁微调了，直接推倒重写你的提示词。

在这个梳理想法的过程中，你同样可以让 Agent 搭把手。我很喜欢认知科学家 Andy Clark 提出的区分：到底是“委托（Delegating）给 AI 系统”，还是与它**[深度协作（Collaborating）](https://pubmed.ncbi.nlm.nih.gov/40389440/)**。在后者这种模式下，你们会进入一个双向增强的良性循环：你的提示词打磨出了更好的输出，更好的输出反过来激发你写出更精准的提示词，进而不断深化你对整个问题的认知模型。如果思路还不清晰，就让 Agent 像记者采访一样，针对它没看懂的地方对你进行连环追问。如果在结束会话时，你感觉自己脑子里的思考模型变得更清晰了，那就是一次成功的协作。

同时，要格外小心“二手输入”的陷阱。在多 Agent 协作时，很容易出现每个 Agent 都只把上一个 Agent 的“摘要”传进上下文的情况，用不了几轮，第三个 Agent 压根就没读过原始文档，信息早就失真了。

你还得为产出立下自己的审美标尺。我用 AI 折腾过各种不同的创意媒介，但绝大部分作品从来没对外发过，因为它们达不到我的标准。现在 AI 吐出来的东西个个精致体面、言之凿凿，这种“精致感”已经失去了区分作品优劣的价值。

**AI 确实让生产变得更快了，但如果某件作品让我觉得“署上我的名字让我感到羞耻”，那我绝不会把它交出去。**

当某次输出没达到你的标准时，顺手把原因记进团队共享的配置文件、钩子（Hook）或测试用例里，确保下次不再犯同样的错。[你的审美标准就是这样一点点沉淀下来、越滚越强的](https://addyo.substack.com/p/agentic-verification)——而且，单纯把“这东西为什么被毙掉”的原因复盘写下来，本身就是极好的思维训练。

## “可是，模型迟早会比我更擅长干这个”

如果你和身边的许多人一样，对这个领域的未来极度乐观，那么在读过去几节时，你脑子里大概已经冒出这个念头好几次了：再过一两年，模型自己就能查出我能查出的所有问题，那我还费劲维持这些技能干嘛？

在“问题检测”这件事上，你说的可能全对，我自己也一直在呼吁把越来越多的检测工作推给 Agent。但我认为人类依然不能躺平的原因在于：**归根结底，必须有人为最终上线的结果负责。** 无论 AI 在过程中帮了多大忙，[**最后站出来担责的，必须是一个活生生的人**](https://addyo.substack.com/p/code-review-in-the-age-of-ai)。

在任何一项具体任务上，究竟该给 Agent 几分信任，这本身就是一道需要人类来做的判断题。而保持这种判断力校准（Calibrated）的方法之一，就是亲自去审查它的工作，因为模型会犯的错误类型一直在动态变化。Anthropic 自己针对内部工程师和研究员的一项研究，就一针见血地指出了这个**[监督悖论（Paradox of supervision）](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)**：

> “想要有效监督 Claude，恰恰需要那些可能会因为过度依赖 AI 而退化的编程技能。”
> 

更重要的是，下面这些对我而言最核心的问题，是再强大的模型也替你回答不了的：

- 你要打造什么？
- 它为什么值得投入？
- 你的目标用户是谁？
- 为了做成它，你愿意做出哪些取舍？

这些问题全都需要你亲自作答。Agent 可以当你的参谋，帮你把思路理顺——我也很乐意它这么做——但拍板的终究是你。

> ⚖️
>
> **终极原则**：你可以把干活的过程外包，甚至把绝大部分的审计工作也外包，但你永远无法外包“责任”。

## 日常练习

上面这些方法，你不需要全盘照搬，挑几个契合你工作流的用起来就行。

- **每周校准练习**：每周抽出一点时间，脱离 Agent 亲手写点代码，或者亲手练一练那些你绝不想生疏的基本功。（我把这叫做**[校准练习](https://addyosmani.com/blog/cognitive-surrender/)**，但这无关标榜自律，纯粹是为了保持手感。）
- **每月技能盘点**：每个月，列一张清单，写下你已经不再亲手做的事情，然后有意识地决定：哪些技能退化了也无妨。我[以前在一篇旧博客里提过的问题](https://addyo.substack.com/p/avoiding-skill-atrophy-in-the-age)，放在今天依然扎心且有效：**如果明天 AI 突然消失了，你会有多手足无措？**
- **拒绝浅尝辄止**：遇到超出你理解范围的东西，老老实实去学。如果我在写东西时碰到一个没见过的新词，我当然可以随手搜个一句话解释直接糊弄过去；但我更倾向于花点时间做点小研究，彻底搞懂它的来龙去脉，好知道它该放在整个知识版图的哪个位置。
- **为审查留出正式工时**：认真检查机器的产出是一份实打实的重活，假装它很轻松，正是许多团队最后干脆放弃检查的根源。审查不是免费的，把它当成正式的排期项（Line item）写进日程表里，你才能真正把它落实到位。

**你停止锻炼的技能终将荒废，而且荒废的速度可能比你想象的还要快。** 那些你不愿舍弃的看家本领，请务必坚持亲手操练。

## 临行锦囊（What to bring with you）

- [ ]  **定好规矩（Be intentional）**：Agent 可以考你、采访你、向你展示证据，但前提是你得先给它设好这些规矩。那就去设好它。
- [ ]  **诚实面对自己在阶梯上的位置**：如果连开着 Agent 帮忙你都解释不清某个答案，那你就是已经“缴械”了。
- [ ]  **先有假设，再行提问**：在开口问之前，先在脑子里立个猜想，哪怕猜得不着边际也行。
- [ ]  **测试全绿不代表真通过**：问清楚它到底测了什么，以及它漏测了什么。
- [ ]  **眼见为实，先看证据**：在读 AI 写的总结报告之前，先看它实际跑了什么命令、吐出了什么原始结果。
- [ ]  **读出它的“潜台词”**：审查时重点看它替你做了哪些隐性决定。
- [ ]  **打磨你的提示词**：你写下的提示词，直接暴露了你对问题到底理解了多少。
- [ ]  **立下底线，绝不妥协**：凡是让你觉得“签上自己大名会让你感到羞耻”的东西，一律不准放行。

亲自下场操练那些真正重要的技能，让自己始终留在牌桌上。你可以从一件小事开始：下次向 Agent 提问前，先写下你预期的结果；等 Agent 干完活后，再写下一件它没检查到的盲点。不妨试试看，这会不会改变你审视 AI 产出的方式。

**独立思考。提出更好的问题。为最终的结果担责。**
